01 / Reconciliation & data quality

Can you trust the revenue number?

Reconcile orders, payments, and refunds into daily net revenue, with invalid records kept out of the analytics layer.

PySpark · SQL · AWS · Airflow

Read the case study ↗

The challenge

Orders, payments, and returns tell different parts of the same story. Joining them at the wrong grain can inflate revenue or count a refund twice.

The decisions

Validate and deduplicate inputs, aggregate before joining, then write Parquet analytics and quarantine datasets. Keep infrastructure definitions and orchestration alongside the pipeline.

The evidence

Four local tests cover revenue reconciliation, invalid refunds, duplicate catalog records, and repeatable reruns. Terraform and an Airflow DAG are included; AWS deployment and Airflow execution have not been performed.

Why this approach?
Problem

A target, not a fixed count

Carrier shares vary by route. A fixed number of carriers would produce different coverage levels.

Decision

Rank, then accumulate

Sort by volume and include the carrier that crosses the threshold. The Python + SQLite implementation uses cumulative SQL rankings; this browser demo uses JavaScript.

Example

80% target → 80% coverage

In the ATL → JFK sample, DL (50%) plus AA (30%) reaches 80%. An 85% target adds UA and reaches 95%.
